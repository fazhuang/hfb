# 01 Project Constitution — 项目宪法

---

> **版本:** V0.1
> **状态:** Draft
> **适用范围:** 全项目 · 全角色 · 强制执行
> **维护者:** 项目负责人 + 技术负责人

## 1. 核心原则

项目所有行为必须符合以下原则。编号越小，优先级越高。

### 原则 1：文档驱动

先写文档，再写代码。文档是设计的工具，不是事后的记录。任何无文档的代码视为不存在。

### 原则 2：不可变历史

已合并的文档不被覆盖。修正用新版本文档取代旧版，旧版标注"已废弃"后保留。

### 原则 3：一人负责

每份文档、每个模块、每个 API 有且仅有一个负责人。负责人对质量和时效性负责。

### 原则 4：可验证性

所有设计决策必须有可验证的输出：代码可测试、数据可校验、AI 结果可溯源。

### 原则 5：学术严谨性优先

功能完整优先于用户体验，数据准确优先于系统性能，可复现优先于创新。

## 2. 文档规范

所有文档遵守以下格式：

- **语言**：中文主体，技术术语保留英文，代码不翻译
- **格式**：Markdown、UTF-8、2 空格缩进
- **版本**：`V0.1` 起步，语义版本 `VMAJOR.MINOR`
- **模板**：使用 `templates/` 中的对应模板
- **引用**：仓库根相对路径，禁止模糊引用

## 3. 技术约束

### 3.1 技术选型原则

- 优先开源、优先社区活跃、优先文档完整
- 不做过度抽象 — 一个模块解决一个问题
- 数据库优先关系型（PostgreSQL），图数据走专用存储

### 3.2 代码规范

- 所有公开 API 必须有文档注释
- 所有数据库迁移必须有回滚脚本
- 所有 AI Prompt 必须版本化管理

## 4. 协作规则

- **分支策略**：功能分支 → PR → 评审 → 合并到主分支
- **提交信息**：`type(scope): description` — 如 `feat(literature): add multi-version import`
- **评审要求**：至少 1 人评审；Constitution 修改需团队评审
- **AI 协作**：Claude 创建 → Codex 审计 → 人审合并

## 5. 质量门禁

| # | 条件 | 阻塞级别 |
|---|---|---|
| 1 | Codex 审计无 Critical 问题 | 阻塞合并 |
| 2 | 新 API 有完整文档 | 阻塞合并 |
| 3 | 数据库变更附 ER 图 | 阻塞合并 |
| 4 | UI 变更通过 Gemini 学术评审 | 阻塞合并（UI 相关） |
| 5 | 无未解决的 Review 意见 | 阻塞合并 |

## 6. 禁止事项

以下行为在任何情况下不被允许：

1. **禁止**无文档的代码合入主分支
2. **禁止**绕过 Codex 审计直接合并文档
3. **禁止**手动修改生产数据库
4. **禁止**将 API 密钥、密码提交到仓库
5. **禁止**在未经评审的情况下修改 Constitution 或 Project Charter
6. **禁止**使用非版本化的 Prompt（即兴 Prompt 不得用于生产）
